# System Requirements Specification

Concise requirements for repository architecture, build behavior, and release networking.

## Functional Requirements
- Root directory contains only the entrypoint, dependency manifests, governance docs, and standard module folders listed in Target Architecture.
- Documentation is centralized under `docs/`, and internal links resolve correctly (no broken links).
- Static media and icons are under `assets/`; scripts and launchers are under `scripts/`.
- Packaging and build scripts are updated to the new paths.
- Version is centralized in `core/version.py` and must reflect the current release.
- Self-contained Server Lifecycle Controls: Both the macOS native menu bar (`NSApp.mainMenu` / toolbar) and the Web UI navigation menu provide responsive Start, Stop, and Restart controls with automatic reconnection polling.

## Build & Release Requirements
- All automated tests pass with no regressions.
- Packaging scripts produce expected dev and release artifacts.
- Release builds must ensure the server runs on ports 80 (HTTP) and 443 (HTTPS). If the platform requires elevated privileges, the release packaging and deployment process must configure either:
  - Direct binding capability (e.g., setcap, service privileges), or
  - A fronting reverse proxy that forwards 80/443 to the app’s configured internal port.
- Build outputs must include clear runtime instructions for production (including port binding or proxy setup).

## Experimental: Xcode Workspace Requirement

The macOS app wrapper is already present in this repository; this experiment validates that its committed `.xcworkspace` opens directly in Xcode and produces a runnable `.app` without additional setup.

Note: This repository is currently a Streamlit project and does not include an Xcode project or workspace by default. For the purpose of this experiment, the goal is to enable opening and running the app via Xcode by introducing a minimal native wrapper that hosts the Streamlit experience.

This experiment passes when a fresh clone can:
1) Open the committed `.xcworkspace` in Xcode,
2) Build and run the wrapper target successfully, and
3) Display the Streamlit UI through the embedded WebView in the mac app without extra manual setup beyond documented steps.

- Always open the workspace: `YourApp.xcworkspace`.
- Do not open: `YourApp.xcodeproj`.
- Fresh clones must be able to open the workspace in Xcode and build without any additional manual steps.

If the workspace is missing in a local clone:
- For CocoaPods projects only:
  1. Install CocoaPods if needed: `sudo gem install cocoapods`
  2. From the repository root, run: `pod install`
  3. Open `YourApp.xcworkspace` in Xcode.
- For Swift Package Manager–only projects, Xcode generates and maintains the workspace automatically when resolving packages. Continue opening `YourApp.xcworkspace`.

Success criteria:
- Opening `YourApp.xcworkspace` immediately shows all targets and schemes.
- The project builds and runs in Xcode without additional configuration.
- Dependencies resolve automatically via Xcode on first open (no extra tooling required beyond the steps above for CocoaPods, if applicable).
